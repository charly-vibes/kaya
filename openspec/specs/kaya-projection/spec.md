# kaya-projection Specification

## Purpose
The compiler that turns the record into readable documentation: generated
content is emitted only inside kaya managed markers, authored prose and
foreign managed blocks are byte-preserved, generation is deterministic, and
rebuilds recompute only what the capture frontier affected. Authored sections
may cite their evidence with `kaya:cites` markers; a section ages only when a
cited fact is corrected — newly arrived evidence never ages it — and the flag
clears only through a human acknowledgment scoped to the block and the cited
ids. Stale flagging is what replaces the silent drift that motivated kaya: the
author finds out their interpretation rests on changed evidence, instead of
never finding out.

## Requirements

### Requirement: Managed block grammar

Documents SHALL mix generated and authored content through two block forms: `<!-- kaya:begin generated:<name> -->` … `<!-- kaya:end generated:<name> -->` for compiler-owned sections and `<!-- kaya:authored -->` … `<!-- kaya:end authored -->` for human-maintained sections. The compiler SHALL regenerate only the content inside generated blocks and SHALL byte-preserve everything outside them, including authored blocks, uncategorized prose, and foreign managed blocks (for example other tools').

#### Scenario: Authored bytes preserved

- **WHEN** a projection regenerates a document whose authored block contains
  interpretation prose
- **THEN** every byte of the authored block and of surrounding uncategorized
  prose is identical before and after regeneration

#### Scenario: Foreign managed blocks untouched

- **WHEN** a document also contains another tool's managed block (for
  example a wai block)
- **THEN** the compiler leaves it byte-identical — kaya owns only kaya
  markers

### Requirement: Deterministic generation

A projection SHALL generate byte-identical sections across runs and machines for identical ledger, graph, and template state — no timestamps of generation, no map iteration order, no locale-dependent formatting inside generated blocks.

#### Scenario: Same inputs, same bytes

- **WHEN** the same dossier is built twice from identical state
- **THEN** the generated sections are byte-identical between the runs

### Requirement: Incremental rebuild

A rebuild SHALL recompute only projections whose inputs changed since the
last build, determined from the event frontier; projections whose inputs
are unchanged SHALL keep their previous bytes without recomputation.

#### Scenario: Unaffected projection untouched

- **WHEN** a new run event arrives and a rebuild executes
- **THEN** the experiment report for the affected experiment is recomputed
  and the research index and unrelated reports keep their prior bytes

### Requirement: Stale-authored flagging

The compiler SHALL report an authored block as stale in the build summary —
naming the changed evidence ids — when the block's cited evidence changes
after its last acknowledgment, and SHALL NOT alter the block's bytes.
Acknowledgment is a human act recorded as an event.

#### Scenario: Evidence change flags the block

- **WHEN** a run event changes counts that an authored interpretation cites
- **THEN** the build summary reports the authored block as stale, naming
  both the block and the changed evidence ids, and the block's bytes are
  unchanged

### Requirement: Citation markers

An authored block MAY cite evidence with `<!-- kaya:cites <id> [<id>…] -->` markers; every cited id SHALL resolve to
an event present in the ledger. A marker naming an unknown id SHALL be refused by
`build` and `check` with a labeled error naming the document, the marker, and
the id. Markers appearing outside an authored block SHALL be treated as
ordinary prose. Marker bytes SHALL never be rewritten.

#### Scenario: Known ids accepted

- **WHEN** an authored block cites an event id present in the ledger
- **THEN** `build` succeeds and staleness detection uses that id

#### Scenario: Unknown id refused

- **WHEN** an authored block cites an id the ledger does not contain
- **THEN** `build` fails with a labeled error naming the document, the marker,
  and the unknown id

#### Scenario: Marker outside an authored block ignored

- **WHEN** a `kaya:cites` marker appears in uncategorized prose
- **THEN** it is left byte-identical and has no effect on staleness

### Requirement: Staleness trigger scope

A cited id SHALL count as changed only when a later event supersedes it and
changes its effective data. Newly appended events that do not supersede a cited
id SHALL NOT mark a block stale. The stale report SHALL name every changed
cited id of the block and SHALL leave the block's bytes unchanged.

#### Scenario: New evidence does not age a block

- **WHEN** a new capture event arrives and no cited id is superseded
- **THEN** the authored block is not reported stale

#### Scenario: Correction ages a block

- **WHEN** an event superseding a cited id changes that id's effective data
- **THEN** the block is reported stale naming the changed id

### Requirement: Acknowledgment events

An acknowledgment SHALL be recorded as one `verification.acknowledged` event
naming the document, the authored block, and the exact cited ids it covers,
with a human actor. Its subject SHALL be typed `Document`; `verification.*`
events are not graph records and the research model SHALL ignore them, creating
no node or edge. An acknowledgment SHALL clear staleness only for that block
and those ids; any unacknowledged changed cited id keeps the block stale. It
SHALL NOT alter authored bytes.

#### Scenario: Acknowledgment clears the covered ids

- **WHEN** a stale block's changed ids are acknowledged in full
- **THEN** the next build reports the block as not stale and the authored bytes
  are unchanged

#### Scenario: Partial acknowledgment leaves the block stale

- **WHEN** only one of two changed cited ids is acknowledged
- **THEN** the block remains stale naming the unacknowledged id

#### Scenario: Acknowledgment is not graph evidence

- **WHEN** an acknowledgment event is replayed
- **THEN** the research graph and generated blocks are identical to their
  state before the acknowledgment

### Requirement: Acknowledgment command

`kaya acknowledge` SHALL append exactly one acknowledgment event when invoked
as `kaya acknowledge <document> --block <name> --events <id>... --actor <name>`,
and SHALL refuse a tool actor with a labeled error, appending nothing. It SHALL
refuse an acknowledgment whose document does not exist or whose block name is
not an authored block in that document. Ids that are no longer cited SHALL be
accepted and SHALL have no effect.

#### Scenario: Tool actor refused

- **WHEN** `kaya acknowledge` is invoked with a tool actor
- **THEN** it fails with a labeled error and appends no event

#### Scenario: Unknown block refused

- **WHEN** `kaya acknowledge` names a document or block that does not exist
- **THEN** it fails with a labeled error and appends no event

### Requirement: Document IR materialization

The compiler SHALL materialize a deterministic document IR between the
ledger-model state and every rendered projection, and SHALL compile every
rendered projection from it. Each record SHALL carry a stable id, a content
hash, and its event ids; records SHALL cover generated documents (family and
kind), authored blocks, and composed records; edges SHALL link a record to
the event ids, cited ids, source artifacts, and contained records it depends
on.

#### Scenario: Containment edges carry transitive impact

- **WHEN** a composed record — a publication page or collection — holds a
  document record
- **THEN** the composed record holds an edge to that document record, so a
  change reaching the document reaches the composed record's impact set

#### Scenario: Identical state yields identical IR

- **WHEN** the document IR is materialized twice from identical ledger,
  graph, and document-source state
- **THEN** both materializations are identical — same record ids, hashes,
  edges, and validation state

#### Scenario: Provenance complete per record

- **WHEN** a generated record is derived from ledger events
- **THEN** the record names those event ids, and the emitted source map for
  its rendered block is exactly that provenance

#### Scenario: Authored block referenced, not copied

- **WHEN** an authored block is modeled in the IR
- **THEN** its record names the document and the block, carries the region
  hash and its cited ids, and stores none of the authored bytes

#### Scenario: IR independent of build caches

- **WHEN** a build cache, stale sidecar, or rendered copy outside the
  document sources is deleted and the IR is materialized
- **THEN** the IR is identical to the materialization before the deletion

#### Scenario: Structure read from the IR, not from rendered markdown

- **WHEN** a structural consumer needs document structure
- **THEN** it reads the IR; rendered markdown is never reparsed to recover
  records or dependencies

### Requirement: Walk-through surface

`kaya ir --walk` SHALL render, read-only, each generated block beside its
body, its provenance resolved against the ledger, and the owning record's
human verification trail, so a human can check a generated block against its
evidence and its recorded review in one command. Unresolvable provenance ids
SHALL be reported as unresolved rather than dropped; corrected evidence SHALL
resolve to the correcting event; trail entries SHALL carry the actor, the
disposition, and digest freshness that is `true` while the bound digest still
matches the record's dependencies, `false` once they change, and `null` when
the event carries no digest — `null` is unknown, never treated as stale.

#### Scenario: Provenance resolves beside the block

- **WHEN** the walk renders a generated block whose provenance names ledger
  events, and the record's input changes after its recorded review
- **THEN** each provenance id resolves to the event's type, subject, actor,
  and timestamp (the correcting event when superseded), and the trail's
  freshness flips from `true` to `false` without any write

#### Scenario: Acknowledgments appear in the trail

- **WHEN** a human acknowledges an authored block and the walk renders it
- **THEN** the trail carries the acknowledgment with its actor, the
  `acknowledged` disposition, and `null` freshness

#### Scenario: Unresolved provenance is flagged, not dropped

- **WHEN** a provenance id names nothing in the ledger
- **THEN** the walk reports that id as unresolved and still renders the rest
  of the block
